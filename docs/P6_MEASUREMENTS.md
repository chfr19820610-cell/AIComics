## 2026-11-16 01:45 · 帧数与耗时关系（重要）

### 实测

| frames | 秒数 | 耗时 | 例 |
|---|---|---|---|
| **39** | 1.62s | **6.3 分钟** | E01/S10 |
| **73** | 3.04s | **11.6 分钟** | E01/S09 |

**结论：耗时与帧数近似线性**（39→6.3min, 73→11.6min，比值 0.54 vs 帧数比 0.53）

### 为什么

**DiT 序列长度 = frames/8（latent）+ 空间 patch**
- 序列越长，每步 attention 计算量越大
- 但主要还是**权重加载**占大头（0.62 GiB DiT）

### 对总时长的影响

**原预估（全 frames=73）**：840 × 11.6 分钟 = **162 小时**

**实际（E01 的分布）**：
- 62 镜 frames=73 × 11.6 = 719 分钟
- 3 镜 frames=56 × 约 9 = 27 分钟
- 5 镜 frames=39 × 6.3 = 32 分钟
- E01 总计约 **13 小时/集**
- 12 集 = **156 小时**

**加上 Round 12 的台词占比修复（短镜变长）**：
- E02-E12 的短镜从 1.62s → 2.33s（frames 39→56）
- 每集约 +13.5 分钟
- 11 集 × 13.5 = **+2.5 小时**
- **总计约 158-160 小时**

### 优化空间（如果将来需要）

**降低 frames 能显著省时间**：
- 全部用 frames=39（1.62s）：840 × 6.3 = 88 小时
- 但 1.62s 太短，叙事撑不住

**折中：frames=56（2.33s）**：
- 840 × 9 = 126 小时（省 32 小时）
- 2.33s 对多数镜够用

**但"3 秒/镜"是漫剧的行业惯例**（观众节奏感），不建议降。

## 2026-11-16 01:57 · 续传验证（优雅 kill 修复的实证）

### 实验设计
Round 15 压力测试（`kill -9`）→ S11 从 step 1 重跑
Round 17 重启（`kill` SIGTERM）→ 预期从 checkpoint 续传

### 实证数据（S11 的 checkpoint 时间线）

| 文件 | 时间 | 阶段 |
|---|---|---|
| latents-step-0001.npz | 01:41 | kill 前 |
| latents-step-0002.npz | 01:42 | kill 前 |
| **latents-step-0003.npz** | **01:45** | **kill 时状态** |
| **latents-step-0004.npz** | **01:51** | **✅ 重启后从 step 4 继续** |
| latents-step-0005.npz | 01:52 | 续传中 |
| latents-step-0006.npz | 01:53 | 续传中 |
| latents-step-0007.npz | 01:54 | 续传中 |
| latents-step-0008.npz | 01:55 | 完成 |

### 结论

**✅ 续传生效**：step 4-8 的时间（01:51-01:55）明显晚于 step 1-3（01:41-01:45），
证明新进程从 step 4 继续，而非从 step 1 重跑。

**节省**：3 步 × 71s = **3.5 分钟**

### 为什么 kill -9 不行

h3stream 的续传依赖 `state.json` 的 `completed_step` 字段。
`kill -9`（SIGKILL）无法捕获，进程立即死 → `state.json` 停留在旧值或损坏。
`kill`（SIGTERM）可捕获 → 写入最新 state → 续传成功。

### 硬规则（新增）

> **重启 h3stream 必须用 SIGTERM（`kill`/`pkill`），禁止直接 `kill -9`。**
> 只有在 SIGTERM 等 5 秒后进程仍在时才用 `-9`（并接受丢 checkpoint 的代价）。

## 2026-11-16 08:02 · prompt 特殊字符安全性检查

### 检查背景

h3stream 命令用双引号包裹 prompt：
```bash
--prompt "$STYLE, $ANTI, $en"
```

如果 `$en` 含特定字符，会破坏命令：
- `"` → 提前闭合双引号
- `$` → shell 变量展开
- `` ` `` → 命令替换
- `\` → 转义

### 检查结果（840 条 prompt）

| 危险字符 | 数量 | 状态 |
|---|---|---|
| **双引号 `"`** | **0** | ✅ 安全 |
| **美元符 `$`** | **0** | ✅ 安全 |
| **反引号 `` ` ``** | **0** | ✅ 安全 |
| **反斜杠 `\`** | **0** | ✅ 安全 |
| **非 ASCII** | **0** | ✅ 安全 |
| 单引号 `'` | 277 | ✅ **在双引号内安全** |

### 关于单引号（277 个）

**来源**：英文所有格（如 `Lin Zhao's`、`Zhao Qian's`）

**为什么安全**：
```bash
--prompt "...Lin Zhao's face..."
```
单引号在**双引号内部**不具特殊含义，只是普通字符。

**只有当**在外面用单引号包裹时才危险：
```bash
--prompt '...Lin Zhao's face...'  # ❌ 会截断
```

**我们用的是双引号，所以安全。**

### 全部字符集（55 个）

```
空格 ' , - . : A-Z a-z
```

**只有英文字母、空格、撇号、逗号、句号、冒号、连字符。**

**极简字符集，无任何危险字符。**

### 结论

**840 条 prompt 无任何命令注入/解析风险。**

### 教训

**检查脚本要区分"在什么上下文里危险"**：
- 单引号在双引号内 → 安全
- 单引号在单引号内 → 危险

**不能一刀切地标记字符。**
